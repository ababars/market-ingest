# vps — раскатка сервера под сбор биржевых данных

Тулкит на bash: один раз заполняешь `.env`, дальше две команды превращают голый
VPS (Ubuntu 24.04, root + пароль) в настроенный сервер с ClickHouse и мониторингом.

Целевая машина: **6 vCPU / 12 GB RAM / 200 GB SSD**, Ubuntu 24.04 LTS.

---

## Руками — только это

1. Создать VPS у хостера, выбрать **Ubuntu 24.04 LTS**.
2. Записать **IP** и **пароль root** из письма/панели.
3. Скопировать конфиг и заполнить:

```bash
cd ~/Documents/cali/vps && cp .env.example .env && chmod 600 .env && vim .env
```

Минимум, что надо вписать: `VPS_HOST`, `VPS_ROOT_PASS`. Остальное имеет
рабочие дефолты.

Всё остальное — скриптами.

---

## Раскатка

```bash
./bootstrap.sh
```

Локальный этап: заливает публичный ключ на root по паролю, пиннит host key,
пишет `Host`-блок в `~/.ssh/config` и алиасы тоннелей в `~/.bash_aliases`.
Для первой заливки нужен `sshpass`:

```bash
sudo apt install sshpass
```

```bash
./provision.sh
```

Удалённый этап: упаковывает этот каталог в tar, кладёт в `/root/vps-provision`
и прогоняет шаги по порядку. Весь вывод дублируется в `./logs/` локально и в
`/var/log/vps-provision/` на сервере.

После первого успешного прогона **очисти `VPS_ROOT_PASS` в `.env`** — ключ уже
на месте, пароль больше ничего не даёт, только лежит на диске.

## Шаги

| Шаг | Что делает |
|---|---|
| `00-base` | `apt upgrade`, базовый CLI, chrony (точное время — критично для биржевых таймстемпов), swap 2 GB со `swappiness=10`, sysctl под ClickHouse и долгие websocket-фиды |
| `10-user` | Непривилегированный пользователь, `sudo` без пароля, тот же SSH-ключ, что у root |
| `20-hardening` | `sshd_config.d`-дропин (пароли выключены), ufw (наружу открыт только SSH), fail2ban, автоматические security-обновления **без** авто-ребута |
| `30-tools` | git, htop, mc, tmux, vim, less, bash-completion + дотфайлы (твой `tmux.conf`, серверный `vimrc`, отдельный цветной PS1) |
| `40-docker` | Docker CE + compose v2 из репозитория Docker, ротация логов контейнеров |
| `50-clickhouse` | clickhouse-server на `127.0.0.1`, память под 12 GB, TTL на системные таблицы, пароль для `default`, база `market` |
| `60-netdata` | Netdata на `127.0.0.1:19999`, коллектор ClickHouse, опционально — Netdata Cloud и Telegram-алерты |
| `99-summary` | Отчёт: версии, диск, память, сервисы, **кто реально слушает порты**, статус ufw |

Отдельный шаг или несколько:

```bash
./provision.sh 50-clickhouse
```

```bash
./provision.sh 30-tools 60-netdata
```

## Доступ

Наружу открыт **только 22-й порт**. ClickHouse и Netdata слушают loopback и
ходят через SSH-тоннель.

```bash
scali
```

Это алиас: шелл на сервере **и** сразу все пробросы. Пока сессия открыта,
ClickHouse доступен на `localhost:8123` / `localhost:9000`, Netdata — на
<http://localhost:19999>.

Если нужны только порты, без шелла (`-N` = не выполнять команду на сервере):

```bash
scali-ch
```

```bash
scali-mon
```

Чистый шелл без пробросов — `ssh scali` (это `Host`-блок, не алиас).

Пароль ClickHouse — в `/root/.clickhouse-credentials` на сервере. На самом
сервере `clickhouse-client` (алиас `chc`) подхватывает его из
`~/.clickhouse-client/config.xml`, вводить руками не надо.

### Почему `Host`-блок, а не только алиас

Алиас в `.bashrc` знает только интерактивный `ssh`. Блок в `~/.ssh/config`
видят **все**: `scp`, `rsync`, `git`, `ssh -L`, ansible. Поэтому имя `scali`
работает везде, а алиасы оставлены только для тоннелей — там реально нужна
длинная строка с пробросами.

## Мониторинг с телефона

Тоннель с телефона — так себе идея. Правильный путь — **Netdata Cloud**:

1. Завести аккаунт на <https://app.netdata.cloud>, в Space нажать *Connect Nodes*.
2. Скопировать `token` и `room` в `.env` → `NETDATA_CLAIM_TOKEN`, `NETDATA_CLAIM_ROOMS`.
3. `./provision.sh 60-netdata`

Ключевое: агент **сам звонит наружу**, входящих портов не открывается,
ufw остаётся закрытым. Дашборд после этого доступен из браузера телефона и из
их приложения.

Альтернатива без облака — `NETDATA_TG_BOT_TOKEN` / `NETDATA_TG_CHAT_ID`:
встроенные алерты (диск заполняется, память, сервис упал) прилетают в Telegram,
а смотреть графики — через тоннель с ноута. Это дешевле, но без картинки.

## Повторный запуск

Скрипты идемпотентны: гонять их можно сколько угодно. Механики две.

**`write_file`** — рендерит нужное содержимое, сравнивает с тем, что на диске,
и трогает файл только при реальной разнице. Отсюда же берётся селективный
рестарт: сервис перезапускается, только если его конфиг действительно поменялся.
Изменённый файл сохраняется рядом как `.bak.<timestamp>`.

**`mark_done`** — маркеры в `/var/lib/vps-provision/done/` для того, что нельзя
«сравнить и сойтись»: создание swap-файла, генерация пароля.

Пароль ClickHouse при повторном прогоне **не ротируется** — он читается из
`/root/.clickhouse-credentials`. Иначе повторная раскатка молча ломала бы всё,
что уже пишет в базу.

Логи: `./logs/provision-*.log` локально, `/var/log/vps-provision/latest.log` на
сервере.

## Тонкие места

**Порядок файлов в `sshd_config.d/` решает всё.** sshd берёт **первое**
встреченное значение ключа, а не последнее — в отличие почти от всего
остального в Unix. Ubuntu-образы кладут `50-cloud-init.conf` с
`PasswordAuthentication yes`, поэтому дропин с именем `60-*` включается позже и
молча игнорируется: на диске написано `no`, а сервер продолжает пускать по
паролю. Отсюда имя `00-hardening.conf` — префикс тут несущий, а не косметика.

И отдельно: шаг не верит собственному файлу, а проверяет результат через
`sshd -T` (он печатает настройки после раскрытия всех `Include`) и падает, если
`passwordauthentication` не `no`. Написать конфиг и применить конфиг — разные
события.

**Рестарт sshd не рвёт текущую сессию.** Новый конфиг применяется только к
новым соединениям — поэтому `20-hardening` безопасен. Тем не менее перед
рестартом делается `sshd -t`, и при невалидном конфиге шаг падает, ничего не
перезапуская. И отдельная проверка: выключить парольный вход можно только
после того, как у `VPS_USER` реально лежит `authorized_keys`.

**`HARDEN_ROOT_LOGIN=prohibit-password`** (дефолт) — root ходит по ключу, но
не по паролю. Так `provision.sh` остаётся перезапускаемым. Если поставить `no`,
повторная раскатка потребует ходить через `VPS_USER` + `sudo` — скрипт этого
пока не умеет, придётся временно вернуть `prohibit-password` руками.

**Членство в группе `docker` ≈ root**: через сокет можно примонтировать
любой каталог хоста в контейнер. Для машины с одним админом это нормально,
но знать стоит.

**Вложенный tmux.** Префикс `C-a` и локально, и на сервере: чтобы отправить
префикс во внутренний tmux, жать `C-a` дважды (`bind-key C-a send-prefix` в
конфиге это как раз и обеспечивает).

**Переименование `VPS_ALIAS` подчищает старое имя.** `bootstrap.sh` находит
свои блоки, которые указывают на этот же `VPS_HOST` под другим именем, и удаляет
их из `~/.ssh/config` и `~/.bash_aliases`. Блоки для других серверов не
трогаются — сверка идёт по `HostName`.

**`99-summary` показывает listening sockets.** Всё, что висит на `0.0.0.0` или
`::`, доступно из интернета, если ufw вдруг сбросится. Смотреть каждый раз.

## Тесты

```bash
./tests/run.sh
```

Не требуют ни root, ни сервера, ни сети. Проверяют примитивы идемпотентности
(`write_file`, `replace_block`, маркеры состояния) и регрессии на баги, пойманные
при первой раскатке — в первую очередь конвейеры, падающие с SIGPIPE под
`pipefail`. Гонять перед раскаткой на новом сервере.

## Что дальше

Не сделано намеренно — чтобы не гадать за тебя:

- **Схема данных ClickHouse** (таблицы трейдов/стакана, партиционирование по
  дню, TTL на сырые данные). Пока создана только пустая база `market`.
- **Бэкапы.** Для ClickHouse это `BACKUP TABLE ... TO Disk(...)` или
  `clickhouse-backup` + выгрузка в объектное хранилище. Нужен ответ на вопрос
  «куда».
- **Сервис-сборщик** данных с бирж: systemd-юнит или docker-compose.
- **Перенос данных** между серверами — отдельный скрипт поверх того же
  `.env` (`rsync` состояния + `BACKUP`/`RESTORE` для ClickHouse).
